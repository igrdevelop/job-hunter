**Motivation.** Владелец: *«почему мы делаем документы для таких вакансий?»* про строку
`2026-08-24 · Interia · Regular Frontend Developer/ka · React · 96%`. Это не первый раз:
сама колонка Sent содержит ту же претензию пять раз за август —
«Реакт, почему обработали?», «не мой стек. должно было вылететь», «Много Реакта»,
«Реакт, почему мы сделали эту вакансию?», «много React».

## Решения владельца (2026-08-24)

1. **React: только вручную, автоматом — нет.** Авто-хант отсекает React-only; если владелец
   сам присылает ссылку — генерируем без споров. Это НЕ включение react-трека.
2. **Выкат предпроверки:** неделя `warn`, потом флип в `skip`.
3. **Фильтр по seniority — не делаем** (замер против, см. M0).

## Problem

Один симптом (React-only вакансия → полный пакет документов → доставка в Sheets/Drive),
но **два независимых дефекта**. Чинить надо оба: A — это потерянная доставка, B — это
потерянная работа пайплайна.

### A. React-гейт в CLI-ветке срабатывает посмертно

Транскрипт `logs/apply_stdout/2026-08-24_001508_Interia_pl_Group.log` (прод), порядок событий:

```
[apply_agent] Step 3: Calling anthropic/claude-sonnet-4-6...
[apply_agent] LLM OUTAGE (billing/auth) — credit balance is too low
[apply_agent] API outage — falling back to Claude CLI (Pro subscription)
[apply_agent] CLI mode | ...
Package ready: ... Ihar_Petrasheuski_CV_React_2026_EN.pdf     ← docs отрендерены
Stack: React | ATS Score: 96%                                  ← строка трекера записана
[apply_agent] Saved job posting -> job_posting.txt
[apply_agent] SKIP — React-only stack: React                   ← гейт срабатывает ЗДЕСЬ
outcome=ok  exit_code=0  duration_sec=831.0
```

Механика: CLI-скилл (`.claude/commands/apply.md:113`) вызывает `generate_docs.py` **без**
`--no-tracker`, то есть строка в трекере появляется внутри самого CLI-вызова. Проверка
стека стоит только после него ([apply_cli.py:385](hunter/apply_cli.py:385)), поэтому к
моменту срабатывания:

1. документы отрендерены (831 с работы подписки);
2. терминальная строка уже есть → `add_react_skipped` → `_is_known_terminal` → **no-op**;
3. `return` даёт exit 0 → `apply_worker._resolve_outcome` видит `has_successful_entry` →
   **`deliver_apply_now`** → Sheets row 1339 + Drive-папка.

В API-ветке та же проверка (Step 4.5) стоит **до** `generate_docs`, поэтому там дефекта нет
— сравни строку `2026-07-06 InteriaGroup / Junior Frontend Developer/ka / React / SKIP`,
записанную корректно.

**Тот же класс дефекта, ещё два места** (по чтению кода, в проде не наблюдалось):
judge-block ([apply_cli.py:506](hunter/apply_cli.py:506)) и lang-gate-block
([apply_cli.py:563](hunter/apply_cli.py:563)) удаляют PDF/DOCX и делают `return`, но строку
трекера не трогают. Значит родитель по exit 0 всё равно доставит: замирроренная в Sheets
строка с пустым Sent попадёт в очередь на отправку, а на Drive уедет папка без документов.

### B. Детерминированные гейты структурно слепы к «react-first, angular вскользь»

`is_react_only_job_text` (Step 1.5c) по контракту консервативен: любое упоминание
«angular» → False. У Interia в тексте **angular 4 раза, react 17 раз**. Замер по всем
августовским случаям, где документы всё-таки сгенерировались на React-стек:

| Дата | Компания | ang / react в тексте | поймал бы 1.5c? |
|------|----------|---------------------|-----------------|
| 08-12 | LanceSoftEurope | 0 / 2 | нет (порог ≥3) |
| 08-12 | ITFS | 0 / 2 | нет (порог ≥3) |
| 08-14 | GeckoDynamics | 1 / 15 | нет (angular есть) |
| 08-20 | Aigorithmics | 4 / 3 | нет |
| 08-21 | HelloFresh | 4 / 17 | нет |
| 08-22 | LeadtechGroup | 2 / 11 | нет |
| 08-24 | Interia | 4 / 17 | нет |

**0 из 7.** Подкрутить пороги/ввести отношение react/angular — путь в ложные срабатывания:
Aigorithmics (4/3) — реально смешанная вакансия, а LanceSoft (0/2) не ловится никаким
счётчиком. Стек по-настоящему известен только после того, как его извлёк LLM — то есть
после того, как работа уже сделана. Это и есть дыра, которую закрывает предпроверка на
дешёвой модели (идея владельца, 2026-08-24).

## Non-goals

- **Не включаем react-трек.** Решение 1: авто — отсекаем, ручная вставка — генерируем.
- **Не строим фильтр по seniority** (решение 3, замер в M0 против).
- Не трогаем правила doomed gate и листинговые фильтры.
- Не рефакторим пайплайны в один раннер (docs/quality/05).
- Предпроверка судит **только про стек**. Локация/язык/авторизация уже за doomed gate;
  seniority кладём в отчёт как поле, но решение по нему не принимаем.

## M1 — CLI post-generation abort ✅ DONE (детерминированно, $0)

Первая веха и единственная безусловная: не зависит ни от предпроверки, ни от решения по
React — чинит утечку доставки саму по себе, включая judge-block и lang-gate-block.

| Файл | Изменение |
|------|-----------|
| `hunter/tracker.py` | Новая `convert_own_applied_row(url, status, sent)` — по образцу `_convert_own_fail_row`: обновляет **свою** applied-строку на месте (id и `sheets_row` сохраняются, `sheets_dirty=1`), а не вставляет вторую |
| `hunter/apply_shared.py` | Новая `abort_after_generation(folder, url, *, reason, telegram_text)`: удалить `*.pdf`/`*.docx` → `convert_own_applied_row(url, "SKIP", "—")` → `notify(...)`. Одна функция на все три места |
| `hunter/apply_cli.py` | **Четыре** места (react-only, company+title дедуп, judge block, lang-gate block) зовут её вместо inline-кода |

**Дедуп-место найдено замером 2026-08-24, не по чтению кода.** Из 14 прогонов полного
`main_cli` в окне **6 не получили вердикта и ни одного раунда refine** — все шесть уткнулись
в посмертный гейт: React ×4 (HelloFresh, Leadtech, Aigorithmics, Interia) и company+title
дедуп ×2 (Ness Solution `nesssolution|javascriptdeveloper`, Grupa Com40). Каждый из них
записал в трекер **самооценочный** балл CLI-скилла (96%, 96%, 78%…) — ровно то число,
которому проект решил не доверять, ради чего и заведён независимый вердикт — и был
доставлен. Для сравнения, на API-пути в том же окне: mean вердикта 90.1 при 1.3 раундах
refine на прогон.

**Родительский процесс менять не нужно.** `_resolve_outcome` сначала проверяет
`has_successful_entry` ([apply_worker.py:64](hunter/apply_worker.py:64)); после конверсии
строка становится SKIP → ветка `_is_known_terminal` → **доставки нет**. Новый exit-код не нужен.

Строку оставляем SKIP (не удаляем): `Sent='—'` держит дедуп, иначе вакансия вернётся на
следующем ханте.

**Тест:** `tests/test_apply_cli_abort.py` — после `main_cli` (а) PDF в папке нет, (б) строка
`ats_status='SKIP'`, `sent='—'`, id прежний, (в) `has_successful_entry(url)` False. Плюс
mutation-verify.

**Rollback:** revert коммита, данные не мигрируют.

## M2 — Явный признак «ручной запуск» (`--manual`) ✅ DONE

Нужен решением 1: авто-поток и ручная вставка должны расходиться по поведению, а сегодня
`apply_agent` их не различает — единственный override это `/force` (`skip_dedup`).

Сигнал де-факто уже есть, но семантически неверный: `run_apply_agent_for_url` (ручные пути —
вставка URL, кнопка Apply, LinkedIn-батч) всегда добавляет `--notify-start` и никогда не
передаёт `--company/--title`, а `run_apply_agent_subprocess` (авто-хант/воркер) наоборот.
Использовать это как маркер — хак; заводим честный флаг.

| Файл | Изменение |
|------|-----------|
| `hunter/services/apply_service.py` | `run_apply_agent_for_url` добавляет `--manual` |
| `apply_agent.py` | `parse_apply_cli_argv` → `is_manual`, прокидывается в `main()` → `main_api`/`main_cli` |
| `hunter/apply_api.py`, `hunter/apply_cli.py` | Все **стековые** гейты (Step 1.5c, Step 4.5, CLI-аналог) при `is_manual` деградируют до warn: сообщение в Telegram + генерация продолжается |

**Важная граница.** `--manual` ослабляет **только стековые** правила. HARD-правила doomed gate
(локация / авторизация / язык) при ручной вставке продолжают блокировать — это отдельно
откалиброванное решение (docs/DOOMED_GATE_PASTE_PLAN.md: исключение для paste убрали именно
потому, что на вставленных постингах терялись реальные деньги). Стек — другой случай: владелец
видит заголовок вакансии, когда шлёт ссылку, и его намерение однозначно.

**Тест:** параметризация обоих режимов — React-постинг: авто → SKIP-строка, `--manual` →
генерация + warn. `/force` продолжает обходить всё.

## M4 — Предпроверка в пайплайне, режим `report` (Step 1.5h)

Новый `hunter/prescreen.py`, один вызов `JUDGE_MODEL` **после** doomed gate (детерминированное
и бесплатное — первым) и **до** первого генерационного вызова, в обеих ветках.

Контракт (структурный JSON, как у judge):

```json
{"primary_stack": "react", "secondary": ["next.js"],
 "angular_required": false, "seniority": "mid",
 "verdict": "mismatch", "confidence": 0.0-1.0, "evidence": "<дословная цитата>"}
```

- Вызывается **только** если `active_tracks()` не покрывает `primary_stack`; при активном
  react-треке — no-op, как и остальные React-гейты (docs/quality/09).
- `PRESCREEN_MODE`: `report` → `warn` → `skip`. Та же схема выката, что у doomed gate и judge.
- При `--manual` (M2) вердикт `mismatch` всегда деградирует до warn, в любом режиме.
- `evidence` обязана быть дословной подстрокой постинга — иначе вердикт отбрасывается
  (нейтрализация галлюцинаций, приём из `claim_judge`).
- Обёрнута в `best_effort("apply.prescreen")`: недоступная модель = «нет вердикта,
  продолжаем», никогда не блокирует.
- `/force` обходит.

## M8 — Узкая унификация: один пост-генерационный блок

Не полный stage-runner из docs/quality/05, а его самая доходная часть.

**Замер, обосновывающий границу (2026-08-24).** С момента написания 05 (15.07) все четыре
файла выросли: `apply_api` 1039→1163 (+12%), `apply_cli` 776→889 (+15%), `apply_shared`
1879→1961, `dual_apply` 516→593 (+15%). В `hunter/` 17 комментариев «mirror of apply_api
Step X» / «parity with the API pipeline», **12 из них в одном `apply_cli.py`**. 15 записей из
123 в AGENT_LOG (12%) касаются обеих веток.

При этом **все** наблюдаемые расхождения живут в пост-генерационном блоке (после того как
`content.json` существует): scrubs → judge → lang gate → дедуп → стек-гейт → render →
verdict → refine → outreach → штампы трекера. До-генерационная часть (fetch → expired →
doomed gate → repost gate) уже расшарена через `apply_shared` и **не дала ни одного
инцидента**. Значит унифицировать надо ровно этот блок, а не весь пайплайн.

Форма: одна функция `hunter/apply_post.py::run_post_generation(ctx, *, policy)` — обе ветки
зовут её вместо своих зеркальных последовательностей. `policy` — это те самые два параметра,
которые 05 и называет единственной реальной разницей между ветками: как блокировать
(API `sys.exit(0)` vs CLI delete-docs+return) и нужен ли пере-рендер после правки контента
(в API контент правится до рендера, в CLI — после).

**Странглер, по одной стадии на PR**, с хвоста: outreach → verdict+refine → render →
гейты → judge → scrubs. После каждого PR — M7-сценарии и существующий API-golden зелёные,
ассерты не правятся (в этом их смысл).

**Что НЕ делаем здесь:** stage-runner как движок, свёртывание `dual_apply` третьей копией,
разбор `apply_shared` по домам, `print()` → `logger`. Это остаётся в docs/quality/05 и
делается отдельно, если и когда обе ветки решено держать долго.

**Критерий готовности:** `grep -rn "mirror of\|parity with" hunter/apply_cli.py` → 0;
новая пост-генерационная стадия добавляется в **одном** месте.

## Что нашлось по ходу (сверх плана)

Три ревью и золотой тест нашли то, чего в плане не было. Всё закрыто в этой же
ветке, каждое — своим коммитом:

1. **Гейт доставки стоял в одном родителе из четырёх.** `deliver_apply_now`
   статус строки не проверял вовсе; из четырёх вызывающих его мест только
   `apply_worker` смотрел в трекер. Ручная вставка, LinkedIn-батч и
   `_auto_apply_all` доставляют по голому exit 0 — то есть отменённый пакет всё
   равно уезжал в Sheets и на Drive. Проверка перенесена в `delivery.py`.
2. **Конверсия по URL — no-op для всего paste-потока**, и там же молчал фолбэк
   (`_is_known_terminal` матчит company+title несконвертированной строки).
   Идентичность взята из `content.json` (`apply_url` / `output_folder`).
3. **Матч по хвосту `дата/компания` конвертировал ЧУЖИЕ строки** — ревьювер
   воспроизвёл на живом трекере, как abort одной вакансии переписывает в SKIP
   другую, уже доставленную. Матч теперь строго по равенству, при
   неоднозначности не трогается ничего.
4. **MANUAL — не «не заявка».** `add_manual_jobleads_pending` всегда писал
   папку; включение MANUAL в блок-лист отрезало JobLeads-потоку и доставку, и
   Drive.
5. **Дедуп-гейт в CLI-ветке совпадал сам с собой** (нашёл golden-тест M7 с
   первого запуска). `generate_docs` пишет строку внутри вызова скилла, а
   `get_known_company_titles()` возвращает все строки. Подтверждено на проде:
   у `Ness Solution` и `Grupa Com40` ровно по одной строке с их ключом —
   записанной тем самым прогоном, который на ней и оборвался. С 21 августа ни
   один CLI-apply, прошедший стековый гейт, дедуп не переживал.
6. **M6 пересмотрена целиком.** Наблюдавшиеся инциденты шли по ветке, которую
   первая версия не меняла, зато в двух других она снимала все ограничители
   ретрая. Осталось: правило в промпте (плюс исправленное противоречие с Шагом
   2), порог короткого текста в `main_cli`, и разделение «папка есть, документов
   нет» — как abort, а не как ретрай.

## Cost

**Оговорка (важная, владелец 2026-08-24 остаётся на CLI-подписке):** цифры в долларах ниже —
из API-эры (277 строк с `cost_usd`). Сейчас прод обслуживается подпиской, `cost_usd` пуст по
построению, и впустую тратятся не доллары, а **время очереди и квота подписки**.

| | На вакансию | Комментарий |
|---|---|---|
| Полная генерация — деньги (API-режим) | $0.349 median | M0 |
| Полная генерация — время (CLI-режим) | **831 с** | замер на самом Interia-прогоне |
| Предпроверка Haiku | ≈$0.0016 / один короткий вызов | 1.5k вход + ~150 выход по median-постингу |

При текущем темпе (~0.3 React-генерации в сутки) предпроверка срезает ≈14 минут очереди в
сутки ценой одного дешёвого вызова на вакансию. Пока прод на подписке главный выигрыш —
пропускная способность очереди и отсутствие мусорных пакетов на разбор, а не доллары; при
возврате на API добавится ≈$0.10/сутки экономии. Вызов меняет реальное решение (генерировать
или нет) до траты работы — условие «никаких спекулятивных LLM-слоёв» соблюдено.

## Проверенные факты о CLI-режиме (замер 2026-08-24, 60 транскриптов)

Владелец спросил, проходят ли круги вердиктов и оценок на CLI. Ответ — **да, оба**:

- **Слой 1, фоллбэк внутри `llm_client` (46 из 60 прогонов):** пайплайн остаётся API-режимом,
  через `claude -p` уходят отдельные вызовы с закреплённой моделью
  (`[LLM] outage on claude-haiku-4-5-20251001 — served via Claude CLI fallback`).
  Отрабатывает всё: ATS-цикл, judge, PDF-вердикт, refine до 5 раундов.
  Smart Working 23.08: `75 → 88 → (откат 74) → 94 → 96`.
- **Слой 2, полный `main_cli` (14 из 60):** вердикт и refine тоже идут —
  ProService 20.08: `70 → 78 → (откат 72) → 93 → …`. Гейт `LLM_API_KEY` пройден (ключ есть).
- **Теряется вердикт только на ранних выходах** — как раз React-скип (Interia), который
  возвращается до стадии вердикта. Покрытие за август: 95 вердиктов из 126 applied-строк.
- **Cost $ на CLI пуст по построению** (подписка не даёт потокенной видимости) — разрезы по
  деньгам и skill `cost-audit` слепнут, пока прод на подписке.

Это отменяет более раннее утверждение (в первой редакции этого документа), будто на CLI
вердикты не пишутся: неверно было только про вердикт, про `cost_usd` — верно.
