# Другие эксперты — кого ещё стоит «пригласить» и зачем

**Status:** draft
**Date:** 2026-09-09
**Motivation:** первые четыре взгляда (PO, маркетинг, архитектура, инженерия)
и четыре приглашённых аудита (безопасность, эксплуатация, комплаенс, данные)
покрывают «можно ли это продать и не сломается ли». Ниже роли, чьё мнение
меняет решения, но которых в проекте пока нет ни в каком виде. Для каждой:
что она посмотрит, что скорее всего найдёт, и мини-план. Ранжировано по
тому, насколько рано её выводы нужны.

## 1. Рекрутер / HR-практик

**Зачем.** Вся система оптимизирует под число, которое ставит модель. Никто в
проекте не спрашивал человека, который реально открывает 200 CV в день.
Ключевые вопросы: сколько секунд на CV; читают ли cover letter вообще; как
относятся к очевидно AI-генерированным текстам; что делает их ATS с PDF
(парсит ли двухколоночный макет, что с польскими диакритиками); важна ли
RODO-клауза; что в «to_learn»-навыках выглядит враньём.

**Что скорее всего найдёт.** Cover letter читают в < 20% случаев (ставит под
вопрос затраты на CL); «about me» вообще не нужен; ATS-скор судьи не равен
тому, как Workday ранжирует; двуязычность важна только для польских компаний
среднего размера.

**Мини-план.**
- M0: 3 интервью по 30 минут (скрипт из 12 вопросов), $0.
- M1: если CL читают редко, `--full` режим и CL-review-цикл переводятся в
  «по запросу», экономия токенов измеряется через `generation_runs`.
- M2: чек-лист «как выглядит подозрительно AI-шный текст» превращается в
  правила `content_qa.py` (детерминированно, $0).
- Решение: подтверждает или ломает опору «честность» из `02-MARKETING_PLAN.md`.

## 2. UX-исследователь

**Зачем.** Сайт строился как личная админка (`applications`, `stats`,
`settings`, `files`), потом обрастал профильными вкладками
(`profile-editor`, `profile-uploads`, `profile-test-resume`). Ни один экран не
проходил через постороннего человека.

**Что посмотрит.** Путь «регистрация → загрузка CV → подтверждение → превью →
первая вакансия → документ» с секундомером; экран подтверждения парсера (сколько
полей правят, где путаются); понятность `to_learn`; Telegram-flow `/link`.

**Мини-план.**
- M0: 5 наблюдений в рамках concierge-теста (`01-PRODUCT_PLAN.md` M0.3), запись
  экрана с согласия, метрика time-to-first-document; правило: медиана > 15 мин →
  онбординг переделывается раньше любой фичи.
- M1: карта фрикций → бэклог сайта (`site/docs/`), три верхних чинятся.
- M2: экран «до/после» (продуктовый M5) прототипируется до кода.

## 3. Финансист / unit-economics

**Зачем.** README называет $0.13–0.17 за tailoring, но это до verdict/refine;
июльский инцидент показал $2 записано против $6 реальных; CLI-режим пишет
`cost_usd = NULL`. Тарифы (`02` M6) не должны опираться на неверную
себестоимость.

**Мини-план.**
- M0: `cost-audit` скилл на VPS + разбивка по стадиям из `verdict_history`;
  правило: если p90 стоимости > $1, refine-раунды для клиентов ограничиваются
  2 до появления биллинга.
- M1: модель в таблице: себестоимость (LLM + инфра/пользователь + поддержка),
  цены из `02`, конверсии из воронки → точка безубыточности по числу
  платящих; сценарии B2C и B2B2C.
- M2: метеринг по токенам всегда (включая CLI) как источник COGS (совместно с
  `06` M5 / `08` M1).

## 4. Prompt / LLM-инженер

**Зачем.** `prompts/generation_rules.md` и `judge_rules.md` менялись десятки
раз по инцидентам; нет регрессионного набора; анти-инъекции нет
(`05-SECURITY_PLAN.md` № 7); выбор модели (Sonnet vs DeepSeek) откладывается с
июля.

**Мини-план.**
- M0: `tools/dual_pairs_stats.py` из `08` M2 на существующих ~86 парах;
  правило: если shadow неразличим от primary (< 2σ) при 6× меньшей цене,
  DeepSeek становится генератором, Sonnet остаётся для refine.
- M1: eval harness (`08` M2) как обязательный гейт в `pr.md` для любого
  изменения в `prompts/`.
- M2: anti-injection обёртка (`05` M6) + тест-набор из 20 инъекций.
- M3: разбор промпта на слои (роль, правила, факты кандидата, вакансия, формат)
  с измеримым влиянием каждого слоя на eval.

## 5. QA-инженер (контракты между репо)

**Зачем.** Три репо делят SQLite-таблицы и файловую структуру по «контракту в
трёх копиях docs» (`MULTI_USER_UPDATE.md`: «must stay in sync»). Дрейф уже
случался (`profile_jobs` мигрировала в api до появления consumer в bot).

**Мини-план.**
- M0: список всех точек контакта (таблицы, пути, payload-схемы, `scout_payload`
  фикстуры) с указанием, есть ли на них тест в обоих репо; правило: точка без
  теста хотя бы с одной стороны → M1.
- M1: JSON-schema для `profile_jobs.payload` по kind и для profile-документа,
  фикстуры общие (как `tests/fixtures/scout_payload_v*.json`), тесты в обоих
  репо.
- M2: smoke-сценарий на проде «регистрация → upload → parse → render →
  preview» (site уже имеет `smoke/`), запускается после деплоя любого из трёх.
- M3: nightly контрактный прогон против Postgres-контейнера после `03` M4.

## 6. Customer success / support

**Зачем.** Сегодня все диагностические инструменты (`/fails`, `/health`,
`fail-forensics` агент, логи) доступны только владельцу через Telegram и SSH.
Первый клиент с вопросом «почему нет документа» упрётся в владельца лично.

**Мини-план.**
- M0: список причин, по которым генерация не даёт документа (из
  `apply_failures.jsonl` + SKIP-причины): топ-10 → тексты для пользователя.
- M1: статус задания на сайте с человекочитаемой причиной (`Job.status` +
  `error` из `03` M4), без обращения к владельцу.
- M2: страница «что произошло с моей заявкой» = облегчённый `fail-forensics`
  для админа; SLA ответа на support-email.
- M3: FAQ/help из реальных вопросов concierge-теста.

## 7. Sales (B2B2C)

**Зачем.** Если буткемп-гипотеза (`01` ICP) подтвердится, продажа когорт
требует навыков, которых нет: pipeline, пилоты, договор.

**Мини-план.**
- M0: 3 разговора «о проблеме» без демо; правило: 2 из 3 признают боль
  трудоустройства выпускников как свою → M1.
- M1: one-pager (`02` M5), предложение бесплатного пилота на одну когорту с
  измеримым KPI (доля выпускников с ответом за 30 дней).
- M2: минимальный админ-функционал «организация → места → пользователи»
  (расширение `admin` модуля API).

## 8. Технический писатель

**Зачем.** `CLAUDE.md` 2500 строк, 40+ планов, три репо: это документация для
агентов, не для людей. Пользовательской документации нет вовсе.

**Мини-план.**
- M0: аудит «кто читает что»: владелец, второй разработчик, агент,
  пользователь, партнёр → четыре разных документа.
- M1: реализация `04-ENGINEERING_PLAN.md` M1 (карта/журнал) руками писателя.
- M2: пользовательский help на PL/EN (5 страниц: профиль, вакансия, документ,
  Telegram, приватность).

## 9. Accessibility / i18n

**Зачем.** Публичный лендинг и форма загрузки CV для польской аудитории:
переключение PL/EN, клавиатурная навигация, контраст, `aria` на drag-and-drop
загрузке. Сайт сейчас только EN.

**Мини-план.** M0: Lighthouse accessibility на трёх экранах; правило: < 90 →
M1. M1: Angular i18n (`@angular/localize`) с PL как второй локалью; M2:
WCAG-проход по форме загрузки и экрану подтверждения.

## 10. Специалист по ATS-системам

**Зачем.** Судья оценивает «как ATS», но никто не проверял против реальных
Taleo/Workday/Greenhouse/SAP SuccessFactors парсеров. В CLAUDE.md есть один
косвенный факт (Taleo классифицирует секцию «Other», если переименовать
EXPERIENCE).

**Мини-план.** M0: прогнать 5 сгенерированных PDF через публичные
парсер-демо (Sovren/Textkernel/Affinda trial, Greenhouse test account);
сравнить извлечённые поля с `content.json`; правило: если хотя бы одна
система теряет секцию, макет (`generate_docs.py`) правится до любых
промпт-изменений. M1: таблица совместимости в docs, утверждение «проверено в
X ATS» на лендинге только с доказательством.

## Кого звать не нужно (пока)

- **DevRel / open-source community manager**: репо публичное, но продукт не
  open-core; сообщество вокруг скрейперов создаст поддержку без дохода.
- **Data engineer с Kafka/Airflow**: объёмы (сотни листингов в день) не
  оправдывают; SQLite/Postgres + ночной job достаточно.
- **ML-инженер для дообучения модели**: нет размеченных данных, нет
  объёма; eval harness важнее fine-tuning.
- **Дизайнер бренда** раньше, чем выбрано имя и подтверждён сегмент.
