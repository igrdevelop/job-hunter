# Improvement 2026-09 — серия планов развития к SaaS

**Date:** 2026-09-09
**Что это.** Проект разобран с восьми позиций (четыре роли продуктовой
компании + четыре приглашённых аудита) и для каждой написан план по
конвенции репо (`.claude/commands/plan-doc.md`: Problem → Non-goals → M0 =
бесплатное измерение с правилом решения → M1..Mn → Risks → Cost → Open
questions). Девятый документ: кого ещё стоит привлечь.

Серия не заменяет `docs/SAAS_PIVOT_PLAN_supersedes_PYTHON_CORE_PLAN.md`
(исполнительный план Stage 0–8). Она ставит перед ним продуктовую фазу 0,
вносит три архитектурные поправки и добавляет то, чего в плане пивота нет:
безопасность, эксплуатацию, комплаенс и измерения.

## Порядок исполнения

Планы пересекаются; ниже единая последовательность, в которой каждая работа
делается один раз. Номера в скобках: план.milestone.

### Неделя 0 — немедленно, независимо от всего

1. **Изолировать CLI-агента** (05.M1): убрать `--dangerously-skip-permissions`,
   `--disallowedTools WebFetch,WebSearch`, non-root `USER`. Один день.
2. **Бэкап реальных данных** (06.M1): `Connection.backup()` для двух SQLite +
   restic для `users/` off-host. Один день.
3. **Запустить измерения** (08.M0.1, 08.M0.2, 01.M0.1, 01.M0.2, `cost-audit`)
   на VPS. ≈$1, полдня. Результаты решают судьбу refine-цикла и списка
   источников.

### Недели 1–3 — фаза 0 продукта (без новой инфраструктуры)

4. **Concierge-тест на 5 людях** (01.M0.3) + наблюдение UX (09.2) +
   3 интервью с рекрутерами (09.1). Правило остановки: < 3 из 5 отправили
   сгенерированное CV → Stage 1–8 пивота замораживаются, фокус на качестве.
5. **Гейт провайдеров для non-owner** (07.M2 = 03.П2): CLI-fallback, shadow,
   OpenRouter только владельцу. Нужен до того, как у concierge-пользователей
   появятся документы.
6. **Лимит генераций на пользователя** (05.M3) и **link-коды** (05.M4).
7. **`generation_runs` + `user_events` + `outcome_label`** (08.M1 = 01.M1 =
   06.M5): одна таблица на три плана, backfill ~500 строк из корпуса.

### Недели 3–6 — фундамент (если фаза 0 пройдена)

8. **Документация карта/журнал** (04.M1) и **доменная модель** (03.M1).
9. **`Settings`-объект** (03.M2 = 04.M5 = 06.M6) с тестом «все имена в
   `.env.example`».
10. **`user_id` во всех запросах** (05.M2) вместе с **расщеплением tracker.py**
    (04.M6), файл за файлом.
11. **Erasure одной операцией** (07.M1), **retention** (07.M3), **privacy/terms/consent** (07.M4).
12. **Graceful stop** (06.M3), **dead-man switch** (06.M4).
13. **Ratchet-гейты и быстрый прогон** (04.M2–M4).

### Недели 6–12 — ядро SaaS (план пивота с поправками)

14. **`core.tailor()`** (03.M3 = Stage 1 пивота).
15. **Сервис + Job + Postgres** (03.M4 = Stage 2 с поправкой П1; 06.M7).
16. **Outbox** (03.M5 = Stage 3).
17. **Контрактные тесты между репо** (09.5) до включения сервиса.
18. **Anti-injection в промпте и QA** (05.M6), **SSRF-фильтр** (05.M5).
19. **Eval harness** (08.M2) как гейт на `prompts/`; решение Sonnet vs DeepSeek по dual-парам.

### После — продукт и рост

20. **Бесплатный скор как публичная страница** (01.M3 = 02.M3), лендинг, имя (02.M1).
21. **Онбординг как продукт** (01.M4), **до/после** (01.M5).
22. **Первый отчёт рынка** (02.M2) после 08.M3.0; **market-aggregate** (08.M3.1, 07.M6).
23. **Тарифная страница без платёжки** (01.M6 = 02.M6), первые платежи вручную.
24. **DocumentStore / рендер-воркер** (03.M6, 06.M8), **образы по ролям** (04.M8).
25. **Слияние CLI в core** (03.M8), **проекция `applications` и вывод SQLite** (03.M9).
26. **Биллинг** (Stage 7 пивота), проверка баланса до постановки в очередь.

```
        │
        ▼
01.M0.3 (concierge) ──► решение: строить дальше или чинить качество
        │
        ├──► 07.M2 = 03.П2 (провайдеры)      нужно ДО документов чужим людям
        ├──► 05.M3/M4 (лимиты, link)          нужно ДО чужих чатов
        └──► 08.M1 = 01.M1 = 06.M5 (журнал)   нужно, чтобы тест дал данные
                 │
                 ▼
03.M2 = 04.M5 = 06.M6 (Settings) ──► 03.M3 (core) ──► 03.M4 (service+Postgres) ──► 03.M5 (outbox)
05.M2 + 04.M6 (user_id + tracker split) ──► 07.M1 (erasure) ──► 07.M4 (privacy/terms)
09.5 (контракты) ──► 03.M4
08.M2 (eval harness) ──► любые изменения prompts/
08.M3.0 ──► 02.M2 (отчёт рынка) ──► 08.M3.1 + 07.M6 (aggregate tier)
01.M3 = 02.M3 (скор-страница) ──► 02.M1 (имя/лендинг) ──► 01.M6 = 02.M6 (тарифы)
```

## Сводка открытых вопросов владельцу

Все вопросы по планам сформулированы как да/нет и собраны в конце каждого
файла. Пять, которые блокируют больше всего:

1. Заморозить Stage 1–8 пивота до результата concierge-теста (01)?
2. Postgres на Stage 2, а не Stage 8 (03)?
3. CLI-подписка только для владельца, клиенты только через API с DPA (03/05/07)?
4. Опустить `ATS_VERDICT_TARGET`/`MAX_REFINES`, если 08.M0.1 не покажет сигнала (01/08)?
5. Польша/CEE как первичный сегмент и разговоры с буткемпами в сентябре (01/02)?

## Что НЕ в этой серии

- Конкретные суммы биллинга и платёжный провайдер (Stripe / Przelewy24):
  после первых ручных платежей.
- Продажа поиска вакансий (hunt) клиентам: решение плана пивота §3.1
  подтверждено, возвращается после market-aggregate.
- Юридические тексты как финальные документы: черновики до юриста.
